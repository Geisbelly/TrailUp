# F0 — Medir antes de mexer: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Saber, todo dia e sem depender da API, quais métricas estão certas: cada lote diz por que
caminho chegou, e um catálogo de métricas no banco diz quais estão disponíveis segundo as
invariantes I1–I20.

**Architecture:** Três migrations encadeadas no Postgres (fronteira do CLAUDE.md: nada disto é IA,
nada passa pela API). (1) `telemetria_lotes` ganha `via`/`fallback_motivo`, com `via` inferida por
gatilho para cobrir builds antigos. (2) Catálogo, resultado, amostra e a view de disponibilidade.
(3) Uma função por invariante, o executor e o job do `pg_cron`. O mobile só passa a mandar o
motivo do fallback.

**Tech Stack:** Alembic (SQL cru via `op.execute`), PL/pgSQL, `pg_cron`, pytest (offline SQL +
e2e em Postgres local), React Native/TS com `node --test`.

**Spec:** `docs/superpowers/specs/2026-10-28-metricas-ponta-a-ponta-design.md` (§4.1, §5, §6, §8 F0)

## Global Constraints

- Revisões: `20261029_01` → `20261029_02` → `20261029_03`, com `down_revision` da primeira = a
  cabeça da `main` no momento do PR (hoje `20261026_01`). Se a `main` andar, renumere — o teste
  `test_alembic_tem_uma_unica_cabeca_e_cadeia_continua` precisa continuar verde.
- Toda view nova nasce `security_invoker = on`. Tabela nova nasce com policy no mesmo commit, ou
  com o docstring dizendo que é só de `service_role`.
- Função `SECURITY DEFINER` usa `SET search_path = ''` e nomes qualificados; `REVOKE ALL ... FROM
  PUBLIC, anon, authenticated` e nenhum `GRANT EXECUTE` a papel de cliente.
- `text()` do SQLAlchemy não aceita `:p::tipo` — use `CAST(:p AS tipo)`. `COALESCE(enum, '')`
  estoura — use `coluna::text`. SQL offline do Alembic dobra `%` (desfazer com `.replace("%%","%")`).
- Fuso de agendamento: `America/Sao_Paulo`; o `pg_cron` roda em UTC → 03:30 BRT = `30 6 * * *`.
- Rodada "velha" = mais de **26 h**. Amostra: até **20** ids por invariante. Histórico do resultado:
  **30 dias**. `n_minimo` padrão: **5**.
- Valores de `via`: `api`, `direta`. Valores de `fallback_motivo`: `sem_url`, `rede`, `timeout`,
  `http_4xx`, `http_5xx`, `sem_sessao`, `desconhecido`.
- Ids de invariante com dois dígitos (`I01`…`I20`), para ordenar no `motivo`; a spec escreve I1…I20.
- Não aplicar migration em produção; só PR, nunca merge (CLAUDE.md).

## Review Focus

1. **Build antigo do app** (sem `fallback_motivo`) grava pela via direta → o lote **não pode** ser
   recusado; `via` vira `direta` pelo gatilho e só a I18 falha. (Task 1, e2e.)
2. **Invariante que estoura em vez de contar** (função dependente ausente, como
   `trailup_progresso_percurso` num banco novo) → registrada como `ok = false` com `erro`, e as
   outras continuam rodando. (Task 4, e2e.)
3. **Auditoria parada** (cron desligado, rodada de anteontem) → toda métrica com invariante fica
   indisponível com motivo `auditoria_atrasada`, nunca "disponível". (Task 3, e2e.)
4. **Métrica que exige validação de modelo** sem promoção → indisponível com
   `aguardando_validacao`, mesmo com todas as invariantes verdes. (Task 3, e2e.)
5. **Aluno lendo a amostra** (que tem ids) → 0 linhas; aluno escrevendo no catálogo ou no
   resultado → recusado. (Task 3, e2e com `SET LOCAL ROLE authenticated`.)
