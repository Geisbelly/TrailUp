0001: Vector store do RAG no Postgres com pgvector

  • Status: Superseded by ADR-0002: OpenAI Vector Store para o RAG
  • Date: 2026-08-29

Context

O TrailUp precisa de uma base de evidências para alimentar o RAG usado pelo mentor virtual, sugestões de personalização, intervenções psicopedagógicas e notificações. Essa base requer um vector store para retrieval semântico de chunks enriquecidos.

Restrições do projeto:

  • A API roda no free tier e hiberna; o Postgres não.
  • A API deve permanecer como camada de IA; infraestrutura de filas, cron e entrega fica no banco.
  • A ingestão e chunking de documentos já existem na API (app/ingestion/).
  • O ecossistema já usa Supabase (Postgres + Storage + Auth) como plataforma principal.

Previous Decision

Usar o Postgres do Supabase com a extensão pgvector como vector store do RAG.

Modelo de embedding: text-embedding-3-small (1536 dimensões) da OpenAI, com fallback para embedding equivalente do Google (text-embedding-004) caso necessário.

Alternatives Considered

Vector store dedicado externo (Qdrant, Pinecone, Weaviate)

  • Pros: melhor escalabilidade de retrieval, índices otimizados, suporte a híbrido sparse/dense.
  • Cons: adiciona novo componente de infraestrutura, novo vendor/custo, sincronização de dados e duplicação de regras de acesso.
  • Rejected because: o volume inicial de chunks não justifica a complexidade; manter tudo no Postgres simplifica transações, RLS e operação no free tier.

FAISS/Chroma local em disco/memória

  • Pros: simples de rodar localmente, sem custo de serviço.
  • Cons: não é compartilhável entre instâncias da API, perde estado quando o container reinicia, exige sincronização manual com o banco.
  • Rejected because: a API é stateless e hiberna; o vector store precisa persistir no banco.

Consequences

Positive

  • Mesmo banco de dados, mesmas transações e mesmas políticas RLS.
  • Retrieval disponível mesmo quando a API está hibernando.
  • Caminho de implementação curto: reaproveita a ingestão e chunking existentes.
  • Sem custo adicional de infraestrutura além do embedding.

Negative

  • Carga extra no Postgres; embeddings ocupam espaço em disco.
  • Retrieval muito grande pode exigir upgrade do banco ou migração futura para vector store dedicado.
  • Índices vetoriais consomem recursos durante inserts/updates.

Migration

  • Habilitar extensão vector no Supabase.
  • Criar tabela rag_chunks com coluna embedding vector(1536).
  • Criar índice HNSW ou IVFFlat para busca por similaridade.
  • Implementar invalidação por source_hash para regenerar embeddings quando fontes mudarem.

Traceability

  • Arquitetura: docs/architecture/rag.md
  • Requisito alinhado: base de evidências para RAG no TrailUp.
  • Issues de implementação: a serem criadas no tracker.

Esta decisão foi mantida no histórico porque a migração 20260829_03 já criou o schema local. Novas fontes devem seguir o ADR-0002; o schema rag_chunks pode ser removido em uma migração posterior depois que não houver consumidores do retrieval local.

0002: OpenAI Vector Store para o RAG

  • Status: Accepted
  • Date: 2026-09-09
  • Supersedes: ADR-0001

Context

O TrailUp já possui extração e normalização de documentos, mas o desenho anterior exigia operar pgvector, gerar embeddings e implementar chunking e retrieval próprios. O projeto agora possui um Vector Store gerenciado pela OpenAI para o corpus público do RAG. O id vigente fica só em OPENAI_RAG_VECTOR_STORE_ID, no ambiente do backend (trocado em 04/11/2026).

Decision

Usar o OpenAI Vector Store com a ferramenta file_search da Responses API como camada de indexação e retrieval para documentos públicos.

  • A OpenAI recebe o arquivo original e gerencia parsing, chunking, embeddings e índice vetorial.
  • A API mantém a chave somente no backend e consulta o store por file_search.
  • O Postgres mantém rag_openai_files, um catálogo operacional com a fonte local, IDs remotos, hash, escopo, atributos e status de indexação.
  • O ID fornecido é reservado para scope = publico. Documentos de turma ou de aluno exigem vector store separado por fronteira de confiança ou uma decisão explícita de isolamento; não serão enviados ao corpus público.
  • O pipeline local de extração continua útil para validação, metadados e fluxos legados, mas não gera embeddings nem é o caminho principal de chunking do RAG.

Authorization and data flow

  1. O backend valida formato, tamanho, MIME type, escopo e autorização da fonte.
  2. O backend envia o arquivo à OpenAI Files e o associa ao Vector Store correto.
  3. O backend aguarda status = completed e registra os IDs/status sem salvar a chave ou conteúdo bruto em logs.
  4. No chat, o backend escolhe somente vector stores permitidos para a sessão e monta filtros de atributos quando aplicável.
  5. A resposta é gerada com file_search; as citações retornadas pela OpenAI permanecem associadas à resposta para auditoria.

O store configurado é só público, então toda busca filtra scope = publico (OpenAIRagService.invoke_structured) e upload_public_file carimba esse atributo e recusa outro escopo. Arquivo no store sem esse atributo não é recuperado: um arquivo subido à mão precisa recebê-lo.

upload_public_file registra em rag_openai_files depois de anexar, não reenvia conteúdo com o mesmo source_hash já concluído no store, e desfaz o envio se não conseguir registrar: a exclusão de dados só conhece o que está no catálogo.

Filtros remotos são defesa em profundidade, não substituto da autorização local. O servidor nunca aceita vector_store_id, scope, classe_id ou aluno_id diretamente do cliente sem derivá-los da sessão e das permissões verificadas.

Consequences

Positive

  • Menos infraestrutura e código operacional no Postgres.
  • Sem custo e manutenção de embeddings próprios.
  • Chunking e busca são fornecidos pelo serviço gerenciado.
  • O catálogo local preserva deduplicação, auditoria e vínculo com o domínio.

Negative

  • Dependência operacional da OpenAI e dos limites do Vector Store.
  • Custos e retenção passam a depender da plataforma OpenAI.
  • O banco não consegue fazer joins SQL diretamente com chunks remotos.
  • Isolamento de documentos privados precisa de múltiplos stores ou de uma política rigorosa de atributos e filtros.

Migration

  • Configurar OPENAI_RAG_API_KEY apenas no ambiente do backend. É a chave da conta dona do store, usada na busca, no envio e na exclusão de arquivos. Não recai em OPENAI_API_KEY (uso comum), nem o contrário: são contas e créditos diferentes.
  • Configurar OPENAI_RAG_VECTOR_STORE_ID com o store público já criado.
  • Aplicar a migration 20261024_01_openai_vector_store_registry (revisão 20261024_01, reencadeada sobre 20261022_05 ao trazer o #166 para a main).
  • Não migrar automaticamente os registros de rag_chunks para o store remoto; cada fonte deve ser reenviada com hash e registro idempotente.
  • Manter rag_chunks temporariamente para compatibilidade e removê-lo somente após confirmar que não há consumidores do retrieval pgvector.
